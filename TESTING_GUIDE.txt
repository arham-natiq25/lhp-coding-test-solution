Event Visuals Testing Guide
===========================

Purpose
-------
Use this guide to manually and automatically test every feature implemented for
the Event Visuals coding test.

The main areas to verify are:
- event listing data
- Event Visuals 1 card grid
- Event Visuals 2 agenda/timeline
- event detail page
- local images
- readable locations
- timezone-aware date/time
- date/location/status filtering
- attendee registration
- confirmation emails
- 3-day and 24-hour reminder emails
- automated test coverage


Prerequisites
-------------
1. Make sure the app dependencies are installed.

   PHP dependencies:
   - composer install

   Frontend dependencies, if Node/npm are available:
   - npm install

2. Make sure .env exists.

   If needed:
   - copy .env.example .env
   - php artisan key:generate

3. Make sure the database is migrated and seeded.

   For a quick local test dataset:
   - SEED_ROWS=500 php artisan migrate:fresh --seed

   For a larger realistic dataset:
   - SEED_ROWS=5000 php artisan migrate:fresh --seed

   The seeder can support much larger data, but small values are better for
   manual UI testing.

4. Start the Laravel app.

   Typical command:
   - php artisan serve

   Default local URL:
   - http://127.0.0.1:8000

5. Start the frontend dev server if the project requires Vite assets.

   Typical command:
   - npm run dev

   Note:
   In the current Codex shell, Node/npm were not available on PATH, so frontend
   build/browser testing could not be completed from here. Run these commands on
   your machine if Node/npm are installed.


Core Routes To Test
-------------------
1. Home redirect:
   - http://127.0.0.1:8000/

   Expected:
   - Redirects to /events.

2. Standard event listing:
   - http://127.0.0.1:8000/events

   Expected:
   - Loads the Events/Index page.
   - Shows filter controls.
   - Uses the improved presentation data.

3. Event data API:
   - http://127.0.0.1:8000/events/data

   Expected:
   - Returns JSON.
   - Includes paginated event data.
   - Includes stats.ms and stats.bytes.
   - Each event includes presentation data.
   - Listing JSON should not include the full raw payload.

4. Event Visuals 1:
   - http://127.0.0.1:8000/events-visual-1

   Expected:
   - Loads a visual card grid.
   - Event cards include image, title, description, location, date/time, badges,
     organizer/venue/price information, and a detail link.

5. Event Visuals 2:
   - http://127.0.0.1:8000/events-visual-2

   Expected:
   - Loads an agenda/timeline style layout.
   - Events are grouped by date.
   - Rows show local time, title, location, venue, and metadata.
   - It should feel different from Event Visuals 1.

6. Event detail page:
   - Open any event from Visual 1, Visual 2, or /events.
   - URL format: http://127.0.0.1:8000/events/{event_id}

   Expected:
   - Shows event title, description, status/type badges, date/time, readable
     location, hero image, gallery image, detail facts, attendee form, attendee
     list, and collapsed source payload.

Filtering Test Matrix
---------------------
Filters should work on:
- /events
- /events-visual-1
- /events-visual-2
- /events/data

The minimum required filters are date and location. Status filtering was also
implemented.


Status Filtering
----------------
Manual UI test:
1. Open:
   - http://127.0.0.1:8000/events-visual-1

2. Choose a status such as:
   - published
   - draft
   - cancelled
   - sold_out

3. Apply the filter.

Expected:
- URL query updates with status.
- Results reload.
- Every visible event has the selected status badge.
- Empty state appears if no events match.

Direct API test:
- http://127.0.0.1:8000/events/data?status=published

Expected:
- JSON total reflects only published events.
- Every returned event has status = published.

Repeat on:
- http://127.0.0.1:8000/events-visual-2?status=published
- http://127.0.0.1:8000/events?status=published


Date Filtering
--------------
Manual UI test:
1. Open:
   - http://127.0.0.1:8000/events-visual-1

2. Set From date:
   - 2024-01-01

3. Set To date:
   - 2024-01-31

4. Apply filters.

Expected:
- URL includes from=2024-01-01 and to=2024-01-31.
- Returned events are within the selected date range.
- Visual 1 cards show only matching dates.

Direct API test:
- http://127.0.0.1:8000/events/data?from=2024-01-01&to=2024-01-31

Expected:
- All returned created_time values fall within January 2024 UTC boundaries.
- presentation.time labels should correspond to those event timestamps.

Edge cases:
1. From date only:
   - /events/data?from=2024-01-01

   Expected:
   - No events before 2024-01-01.

2. To date only:
   - /events/data?to=2024-01-31

   Expected:
   - No events after 2024-01-31.

3. Future date range with no records:
   - /events/data?from=2099-01-01&to=2099-01-31

   Expected:
   - total is 0.
   - UI shows an empty state.

Repeat date filtering on:
- /events-visual-2
- /events

Reminder Email Testing
----------------------
Command:
- php artisan events:send-reminders

Reminder windows:
- 3-day reminder: event starts more than 24 hours and up to 72 hours from now.
- 24-hour reminder: event starts from now through 24 hours from now.

Expected:
- Attendees for matching events receive reminder emails.
- reminder_3_days_sent_at is set after a 3-day reminder.
- reminder_24_hours_sent_at is set after a 24-hour reminder.
- Already-sent reminder types are not sent again.


Manual Reminder Test With Tinker
--------------------------------
Use this when you want to create exact reminder scenarios.

1. Open tinker:
   - php artisan tinker

2. Create a user:
   - $user = App\Models\User::factory()->create();

3. Create an event 3 days from now:
   - $event = App\Models\Event::factory()->for($user)->create(['created_time' => now()->addDays(3)->timestamp, 'payload' => ['name' => 'Manual Three Day Test']]);

4. Add an attendee:
   - $attendee = App\Models\EventAttendee::create(['event_id' => $event->id, 'name' => 'Ada Lovelace', 'email' => 'ada@example.com']);

5. Exit tinker.

6. Run:
   - php artisan events:send-reminders

Expected:
- A 3-day reminder is sent.
- event_attendees.reminder_3_days_sent_at is filled.
- event_attendees.reminder_24_hours_sent_at stays null.

For a 24-hour reminder, create the event with:
- 'created_time' => now()->addDay()->timestamp

Expected:
- reminder_24_hours_sent_at is filled.
- reminder_3_days_sent_at stays null.

Common Issues To Watch For
--------------------------
1. Broken frontend assets:
   - Run npm install and npm run dev.
   - Check the browser console.

2. No emails appearing:
   - Use MAIL_MAILER=log.
   - Check storage/logs/laravel.log.

3. No reminders sent:
   - Make sure the event created_time is inside the reminder window.
   - Make sure the attendee does not already have the corresponding reminder
     timestamp set.

4. Slow seeding:
   - Use SEED_ROWS=500 for manual testing.

5. Empty filters unexpectedly:
   - Check that seeded data contains the chosen date/location/status
     combination.
   - Test with a direct API URL first.
